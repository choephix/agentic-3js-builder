Rotation is not one universal 3D convention: each tool fixes its own axes, handedness, forward direction, angle units, and rotation order.
The most consequential differences here are Blender/OpenSCAD Z-up versus three.js/glTF/Unity/Godot Y-up, and Unity/CSS versus right-handed systems.
Euler triples are not portable values: the same three numbers mean different poses when order, intrinsic/extrinsic frame, sign, or units change.
For an LLM-facing builder API, direction/endpoint plus an explicit up/reference vector is easier to state and validate than hand-derived Euler angles.
Use quaternions or orthonormal bases internally; expose Euler only with explicit units, order, and local/world space, and render/check the result.

### What the table means for the observed “sometimes right, sometimes wrong” behavior

- The number `90` is not portable by itself: it can mean degrees (Unity/OpenSCAD), radians (three.js/Godot/Blender Python), or a CSS angle only when paired with a unit. A missing unit can turn a quarter-turn into a tiny angle or a huge one. ([three.js Euler source](https://github.com/mrdoob/three.js/blob/dev/src/math/Euler.js#L25-L35), [Unity Transform.Rotate](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Transform.Rotate.html), [Godot Node3D](https://docs.godotengine.org/en/stable/classes/class_node3d.html), [OpenSCAD rotate](https://en.wikibooks.org/wiki/OpenSCAD_User_Manual/Transformations#rotate))
- A sign that is “obviously clockwise” on a screen is not a 3D rule. CSS explicitly defines its 3D direction as clockwise from the vector end toward the origin, while glTF defines positive rotation as counter-clockwise and Unity’s left-handed diagram uses a stated viewing direction. ([W3C CSS Transforms 2](https://drafts.csswg.org/css-transforms-2/#three-dimensional-transform-functions), [Khronos glTF §3.4](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#coordinate-system-and-units), [Unity rotation manual](https://docs.unity3d.com/2021.3/Documentation/Manual/QuaternionAndEulerRotationsInUnity.html))
- Euler order is part of the meaning. Unity uses extrinsic Z→X→Y; Godot defaults to intrinsic Y→X→Z; three.js and Blender APIs default to XYZ. Copying a triple without copying the order and the local/world frame changes the result. ([Unity rotation manual](https://docs.unity3d.com/2021.3/Documentation/Manual/QuaternionAndEulerRotationsInUnity.html), [Godot Basis](https://docs.godotengine.org/en/stable/classes/class_basis.html), [three.js Euler source](https://github.com/mrdoob/three.js/blob/dev/src/math/Euler.js#L25-L35), [Blender Euler API](https://docs.blender.org/api/current/mathutils.html#mathutils.Euler))
- Primitive assumptions are another silent source of errors: three.js and Unity/Godot cylinders are Y-lengthwise, while Blender and OpenSCAD cylinders are Z-lengthwise. A “make this rod vertical” recipe copied between them can rotate the rod by 90° or 180° unexpectedly. ([three.js CylinderGeometry](https://github.com/mrdoob/three.js/blob/dev/src/geometries/CylinderGeometry.js#L92-L117), [Unity primitives](https://docs.unity.com/en-us/engine/6000.6/manual/working-with-gameobjects/gameobject-fundamentals/primitive-objects), [Godot source](https://github.com/godotengine/godot/blob/master/scene/resources/3d/primitive_meshes.cpp#L1075-L1135), [Blender cylinder operator](https://docs.blender.org/api/current/bpy.ops.mesh.html#bpy.ops.mesh.primitive_cylinder_add), [OpenSCAD cylinder](https://en.wikibooks.org/wiki/OpenSCAD_User_Manual/Primitive_Solids#cylinder))
- Blender is Z-up, while glTF’s required convention is +Y-up. Blender’s glTF exporter exposes a **Y Up** option described as “Export using glTF convention, +Y up”; this is the axis conversion boundary. Do not add an extra hand-written quarter-turn before or after export unless you have verified the actual imported scene. ([Blender glTF exporter](https://docs.blender.org/manual/en/latest/addons/scene_gltf2.html#transform), [Khronos glTF §3.4](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#coordinate-system-and-units))
- glTF assets face +Z, but Godot’s default camera/object forward is −Z, and three.js cameras conventionally look down −Z. A model can be upright but face away from a camera if an importer or author assumes “front” means the same thing in all three systems. ([Khronos glTF §3.4](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#coordinate-system-and-units), [Godot Basis](https://docs.godotengine.org/en/stable/classes/class_basis.html), [three.js Camera](https://threejs.org/docs/pages/Camera.html))
- Symmetry can hide a wrong rotation: a box or a perfectly round cylinder may look unchanged after a 180° flip, while a spike, chevron, roof pitch, tread marker, or one-sided plane exposes it. This is a geometric consequence of object symmetry, not a convention documented by one tool. **[INFERENCE]**

## Pitfalls when moving code and assets

### Blender → three.js and Blender → glTF

1. **Do not treat Z-up and Y-up as cosmetic labels.** A Blender cylinder’s longitudinal Z axis and a three.js cylinder’s longitudinal Y axis are different local geometries. Either construct through a helper that names its axis, or apply one explicit conversion at the import boundary. ([Blender cylinder operator](https://docs.blender.org/api/current/bpy.ops.mesh.html#bpy.ops.mesh.primitive_cylinder_add), [three.js CylinderGeometry source](https://github.com/mrdoob/three.js/blob/dev/src/geometries/CylinderGeometry.js#L92-L117))
2. **Use the exporter’s conversion once.** Blender’s exporter documents **Y Up** as the glTF convention. glTF itself requires +Y up and +Z asset-front. A second “make it Y-up” rotation in application code is a common way to double-convert. ([Blender glTF exporter](https://docs.blender.org/manual/en/latest/addons/scene_gltf2.html#transform), [Khronos glTF §3.4](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#coordinate-system-and-units))
3. **Separate asset-forward from camera-forward.** glTF’s front is +Z; Godot cameras default to −Z and three.js cameras look down −Z. Name an asset’s forward axis in metadata or rotate the root once at the boundary; do not bury the fix in every child mesh. ([Khronos glTF §3.4](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#coordinate-system-and-units), [Godot Basis](https://docs.godotengine.org/en/stable/classes/class_basis.html), [three.js Camera](https://threejs.org/docs/pages/Camera.html))
4. **Convert units at the same boundary as axes.** glTF linear distances are meters, while Blender scene units can be configured and three.js is unitless by convention. A scale conversion and an axis conversion are separate operations and both need explicit policy. ([Khronos glTF §3.4](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#coordinate-system-and-units), [Blender Scene Units](https://docs.blender.org/manual/en/latest/scene_layout/scene/properties.html#units))

### Euler and screen-space habits

- A prompt that says “rotate 45° clockwise” is underspecified unless it names the axis, viewpoint, handedness, and whether the axis is local or world. CSS’s own spec makes the viewpoint part of the rule. ([W3C CSS Transforms 2](https://drafts.csswg.org/css-transforms-2/#three-dimensional-transform-functions))
- “Rotate around X, then Y, then Z” is also underspecified: Unity’s documented order is extrinsic Z→X→Y, Godot’s default is intrinsic Y→X→Z, and OpenSCAD describes nested transforms with its own X→Y→Z semantics. ([Unity rotation manual](https://docs.unity3d.com/2021.3/Documentation/Manual/QuaternionAndEulerRotationsInUnity.html), [Godot Basis](https://docs.godotengine.org/en/stable/classes/class_basis.html), [OpenSCAD rotate](https://en.wikibooks.org/wiki/OpenSCAD_User_Manual/Transformations#rotate))
- A 2D screen intuition can invert a 3D result because CSS’s positive Y goes down the page and +Z comes toward the viewer. Keep screen-space angles out of a 3D construction API unless the API says it is screen-relative. ([W3C CSS Transforms 2](https://drafts.csswg.org/css-transforms-2/#3d-transform-rendering))

## API design guidance for an LLM-facing 3D builder

### Prefer a direction plus a reference up vector

A useful orientation is “the object’s named forward axis points along this direction, while its up axis is as close as possible to this reference up.” This is what well-known APIs expose:

- Unity’s `Quaternion.LookRotation(forward, upwards)` creates a rotation from `forward` and `upwards`, then derives the other axes with cross products. It documents failure/degenerate cases for zero forward and collinear forward/up. ([Unity `Quaternion.LookRotation`](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Quaternion.LookRotation.html))
- Godot’s `Node3D.look_at(target, up, use_model_front)` takes a target and an up vector; Godot also exposes `Basis.looking_at(target, up)`. ([Godot `Node3D.look_at`](https://docs.godotengine.org/en/stable/classes/class_node3d.html#class-node3d-method-look-at), [Godot `Basis.looking_at`](https://docs.godotengine.org/en/stable/classes/class_basis.html#class-basis-method-looking-at))
- three.js `Object3D.lookAt(target)` rotates an object to face a world-space point and has an `up` property that influences the orientation. ([three.js `Object3D.lookAt`](https://threejs.org/docs/pages/Object3D.html#Object3D.lookAt), [three.js `Object3D.up`](https://threejs.org/docs/pages/Object3D.html#Object3D.up))

For an LLM API, an endpoint operation is therefore less ambiguous than asking the model to derive angles:

```ts
rod({ from: a, to: b, radius });
cone({ tip, baseCenter, radius });
box({ center, size, forward: normalize(to - from), up: WORLD_UP });
```

The builder should document which local axis is “forward” for each primitive and should reject or define behavior for `from == to`, zero direction, and direction/up collinearity. The degenerate cases are not theoretical: Unity explicitly documents them for `LookRotation`. ([Unity `Quaternion.LookRotation`](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Quaternion.LookRotation.html)) **The endpoint recommendation and TypeScript shape above are API-design inferences.**

### Use quaternions or bases as the internal orientation

- Blender’s rotation-mode manual says Euler systems can lose an axis at gimbal lock, while quaternion mode does not suffer gimbal lock and is ideal for interpolating between orientations. ([Blender Rotation Modes](https://docs.blender.org/manual/en/latest/advanced/appendices/rotations.html))
- Unity likewise says it stores rotations internally as quaternions and warns that converting to Euler for calculations risks gimbal lock. ([Unity rotation manual](https://docs.unity3d.com/2021.3/Documentation/Manual/QuaternionAndEulerRotationsInUnity.html))
- The CSS Transforms specification’s matrix decomposition is explicitly based on a method “modified to use Quaternions instead of Euler angles to avoid the problem of Gimbal Locks.” ([W3C CSS Transforms 2 source](https://github.com/w3c/csswg-drafts/blob/main/css-transforms-2/Overview.bs#L1040-L1044))
- Shoemake’s SIGGRAPH 1985 paper introduced quaternion curves for animating rotations; the paper is a primary graphics-literature source for quaternion interpolation. ([ACM record](https://dl.acm.org/doi/10.1145/325334.325242), [paper scan](https://www.cs.cmu.edu/~kiranb/animation/p245-shoemake.pdf))

A practical seam is: accept human-friendly direction/endpoint inputs, construct a quaternion or orthonormal basis once, and keep that representation for child placement and interpolation. **This is API-design guidance, not a claim that every engine uses the same quaternion convention.** glTF and three.js both use `[x,y,z,w]`-style quaternion component storage, but callers still need to verify multiplication order and local forward axis. ([Khronos glTF node](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#reference-node), [three.js Quaternion source](https://github.com/mrdoob/three.js/blob/dev/src/math/Quaternion.js#L1-L20))

### Keep Euler as an explicit escape hatch, not an unlabelled triple

If an API must expose Euler angles, require all of these fields (or equivalent):

```ts
type EulerRotation = {
  x: number;
  y: number;
  z: number;
  unit: "rad" | "deg";
  order: "XYZ" | "XZY" | "YXZ" | "YZX" | "ZXY" | "ZYX";
  space: "local" | "world";
};
```

This shape is an **[INFERENCE]** from the documented failure modes: the tools disagree about units (degrees/radians), order (including intrinsic/extrinsic), and local/world interpretation. It prevents the exact class of “`[90 - a, 0, 0]` copied six times” mistake described in the task by forcing the convention into the data rather than into the model’s memory. ([three.js Euler source](https://github.com/mrdoob/three.js/blob/dev/src/math/Euler.js#L25-L35), [Unity rotation manual](https://docs.unity3d.com/2021.3/Documentation/Manual/QuaternionAndEulerRotationsInUnity.html), [Godot Basis](https://docs.godotengine.org/en/stable/classes/class_basis.html), [Blender Euler API](https://docs.blender.org/api/current/mathutils.html#mathutils.Euler))

### Make primitive axes and frame choices visible

Every primitive helper should document its local axes (`cylinderAxis: 'Y'`, `planeNormal: '+Z'`, or an equivalent named enum), and orientation helpers should name whether `dir` is world-space or parent-local. This is an **[INFERENCE]** from the documented primitive differences and from `lookAt` APIs that distinguish world-space targets/up vectors. ([three.js CylinderGeometry](https://github.com/mrdoob/three.js/blob/dev/src/geometries/CylinderGeometry.js#L92-L117), [three.js PlaneGeometry](https://github.com/mrdoob/three.js/blob/dev/src/geometries/PlaneGeometry.js#L49-L75), [Unity `LookRotation`](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Quaternion.LookRotation.html), [Godot `Node3D.look_at`](https://docs.godotengine.org/en/stable/classes/class_node3d.html#class-node3d-method-look-at))

### Add a visible validation loop

For generated scenes, render or inspect a diagnostic view containing world axes, a forward arrow, an up arrow, and one deliberately asymmetric marker on each oriented part. Compare the marker’s endpoint/direction against the requested relation, not only against whether a symmetric silhouette “looks okay.” This is an **[INFERENCE]** recommendation motivated by the symmetry observation above; it is not a claim that the cited tools provide an automatic validator.
