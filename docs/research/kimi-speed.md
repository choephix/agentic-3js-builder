## What is actually faster

### 1. OpenRouter's Highspeed route (recommended immediate test)

OpenRouter currently exposes two Moonshot AI endpoints for `moonshotai/kimi-k3.1-pro`. Both report `mxfp4` quantization and a 1,048,576-token context. The standard endpoint is tagged `moonshotai/mxfp4` and is priced at $2/M input and $10/M output. The second is tagged `moonshotai/highspeed`, reports the same quantization/context, and is priced at $4/M input and $20/M output. The endpoint object also exposes `reasoning`, `reasoning_effort`, and `max_tokens`, but no speculative-decoding parameter or throughput field. ([OpenRouter endpoint JSON](https://openrouter.ai/api/v1/models/moonshotai/kimi-k3.1-pro/endpoints))

I ran two streamed OpenRouter requests on 2026-10-27 using the existing OpenRouter key and the same prompt: ask for a detailed TypeScript file, `max_tokens=5000`, `reasoning.effort=low`, and provider pinned with `provider.only` (no fallback). The stream's final usage object reported exactly 5,000 completion tokens in each run. Results:

| Route                  |   TTFT | Total wall time | Completion tokens | Reasoning tokens | Decode rate after TTFT | Cost reported by API |
| ---------------------- | -----: | --------------: | ----------------: | ---------------: | ---------------------: | -------------------: |
| `moonshotai/highspeed` | 6.96 s |         68.49 s |             5,000 |            1,661 |         **81.4 tok/s** |            $0.100632 |
| `moonshotai/mxfp4`     | 2.58 s |        166.59 s |             5,000 |            3,062 |         **30.5 tok/s** |            $0.050316 |

These are one-run measurements, not a sustained benchmark. “Completion tokens” includes reasoning tokens as reported by the API; the displayed decode rate is `5,000 / (wall time − TTFT)`. End-to-end rates are 73.0 and 30.0 tok/s respectively. The Highspeed run was 2.7× faster in this test and cost 2× as much for output. The different reasoning-token counts mean the test does not prove identical answer quality or identical internal work; it does show the practical speed/cost trade-off for the requested workload. **[OBSERVED DIRECTLY]**

Artificial Analysis independently reports the same ordering: its K3.1 Pro provider page lists Kimi High Speed at 81.3 output tok/s and Kimi at 41.4 tok/s, with median time-to-first-answer-token of 27.55 s and 51.22 s respectively. It reports blended prices of $2.94/M and $1.54/M under its workload mix. Its page states that speed is measured after the first streaming chunk and latency includes reasoning time. ([Artificial Analysis provider benchmark](https://artificialanalysis.ai/models/kimi-k3-1-pro/providers), accessed 2026-10-27.)

### 2. Moonshot's own API

Moonshot's official K3.1 Pro guide names the model IDs `kimi-k3.1-pro` and `kimi-k3.1-pro-highspeed`, and explicitly says Highspeed delivers 2–3× the speed of K3.1 Pro. K3.1 Pro is always a thinking model; the supported control is top-level `reasoning_effort` with `low`, `high`, or `max` (default `max`). ([K3.1 Pro quickstart](https://platform.kimi.ai/docs/guide/kimi-k3-1-pro-quickstart), [reasoning-effort reference](https://platform.kimi.ai/docs/guide/use-reasoning-effort))

The official pricing table lists:

- `kimi-k3.1-pro`: $2/M input, $10/M output, $0.20/M cached input, $2/M 5-minute cache write, and $4/M 1-hour cache write.
- `kimi-k3.1-pro-highspeed`: $4/M input, $20/M output, $0.20/M cached input, $4/M 5-minute cache write, and $8/M 1-hour cache write.
- `kimi-k3`: $3/M input, $15/M output, $0.30/M cached input, $3/M 5-minute cache write, and $6/M 1-hour cache write.

([Official Kimi API pricing](https://platform.kimi.ai/docs/pricing/chat))

The Open Platform is pay-as-you-go and has no subscription plan. It requires at least a $1 recharge before use; cumulative recharge determines concurrency, RPM, TPM, and TPD tiers. The published tier table increases capacity as recharge rises (up to Tier 5 at $3,000 cumulative recharge), but it does not promise a higher per-request decode speed or a dedicated/high-priority inference lane. Enterprise plans are available through sales. ([Product comparison](https://platform.kimi.ai/docs/guide/product-plans), [rate limits](https://platform.kimi.ai/docs/pricing/limits)) **[INFERENCE]** The published material does not establish that buying a higher tier makes one stream faster.

### 3. Kimi Code subscription

Kimi Code is a separate coding product, not the Open Platform API. Its official documentation exposes coding endpoints at `https://api.kimi.ai/coding/v1` and model IDs `k3.1-pro` and `k3.1-pro-highspeed`; it describes Highspeed as about 2–3× the regular model's output speed and about 2× the quota consumption. New-plan documentation says K3.1 Pro and K3 require Plus or above, while 1M context and Highspeed require Pro or above. API keys are created in the Kimi Code console. ([Kimi Code overview](https://www.kimi.com/code/docs/), [model IDs and endpoints](https://www.kimi.com/code/docs/en/kimi-code/models.html), [membership limits](https://www.kimi.com/code/docs/en/kimi-code/membership.html))

This is a possible route if a subscription is acceptable, but it is not a free speed setting: it requires a Kimi membership, has rolling five-hour/monthly quotas, and the public documentation does not give a numeric tok/s guarantee. **[INFERENCE]** The subscription is useful for access/quota and the Highspeed model, but the measured OpenRouter Highspeed API is the only route tested here.

## K3 provider landscape

K3.1 Pro has only two provider entries in Artificial Analysis's current provider benchmark—Kimi and Kimi High Speed—and the same two endpoint families appear in OpenRouter. ([Artificial Analysis K3.1 Pro providers](https://artificialanalysis.ai/models/kimi-k3-1-pro/providers), [OpenRouter endpoints](https://openrouter.ai/api/v1/models/moonshotai/kimi-k3.1-pro/endpoints))

K3 has a much wider hosted-provider footprint. Artificial Analysis's current K3 provider page (which marks K3 deprecated and recommends K3.1 Pro) lists 17 providers. Its fastest listed results are LithosAI (ULTRA CHAT) **503.4 tok/s**, Inco (FAST) **478.0 tok/s**, Amazon **306.0 tok/s**, LithosAI (FAST) **264.8 tok/s**, and LithosAI **249.3 tok/s**. ([Artificial Analysis K3 providers](https://artificialanalysis.ai/models/kimi-k3/providers), accessed 2026-10-27.)

The first-party provider material I could verify gives the following more cautious picture:

- **Nebius Token Factory:** Its Kimi K3 webinar reports improving single-stream generation from 79 to 120 tok/s and aggregate throughput above 2,600 tok/s under high concurrency. The same page says the configuration used eight NVIDIA B300 GPUs, kernel/communication fusion, speculative decoding, and prefix caching. Its current catalogue lists a public `moonshotai/Kimi-K3` endpoint at $3/M input and $15/M output, and says dedicated endpoint availability is model-specific. It does not publish a K3 tok/s number on the current model page. ([Baseten K3 page](https://www.baseten.co/library/kimi-k3/), [Baseten launch report](https://www.baseten.co/blog/how-to-build-a-day-zero-api-for-kimi-k3/))

## Thinking controls, batching, and speculative decoding

- K3.1 Pro thinking cannot be disabled on Moonshot's official API: the guide says it “always has thinking mode enabled.” The only documented control is `reasoning_effort=low|high|max`; there is no documented arbitrary thinking-budget field. ([K3.1 Pro guide](https://platform.kimi.ai/docs/guide/kimi-k3-1-pro-quickstart), [reasoning-effort guide](https://platform.kimi.ai/docs/guide/use-reasoning-effort))
- The OpenRouter K3.1 endpoint objects advertise `reasoning_effort` and `max_tokens`, but not speculative decoding, draft-model, or priority parameters. ([OpenRouter K3.1 endpoints](https://openrouter.ai/api/v1/models/moonshotai/kimi-k3.1-pro/endpoints))
- On self-hosted K3, official vLLM recipes show a DSpark speculative-decoding setup. Nebius and Baseten independently describe speculative decoding as a speed optimization. This is an infrastructure-level optimization, not a setting exposed by the hosted K3.1 Pro endpoint. ([vLLM K3 recipe](https://recipes.vllm.ai/moonshotai/Kimi-K3), [Nebius webinar](https://nebius.com/events/webinar-kimi-k3), [Baseten K3 launch report](https://www.baseten.co/blog/how-to-build-a-day-zero-api-for-kimi-k3/))
- Prefix/KV caching reduces repeated long-prefix prefill and therefore time to first token; it does not make the model's steady-state decode kernel intrinsically faster. The Kimi API automatically enables context-cache billing for repeated prefixes, and both Nebius and Baseten describe cache-aware serving. ([Kimi pricing](https://platform.kimi.ai/docs/pricing/chat), [Nebius webinar](https://nebius.com/events/webinar-kimi-k3), [Baseten launch report](https://www.baseten.co/blog/how-to-build-a-day-zero-api-for-kimi-k3/)) **[INFERENCE]** For this workload's large mostly-stable system prompt, cache hits may improve TTFT/cost, but they will not turn 30 tok/s decode into Sonnet-like 130 tok/s.

## Open weights and self-hosting

Kimi K3 is open-weight and its official model card reports a 2.8T-parameter MoE, 104B activated parameters, 896 routed experts with 16 selected per token, 93 layers, 1,048,576-token context, and MXFP4 weights/MXFP8 activations. ([Moonshot's Hugging Face K3 model card](https://huggingface.co/moonshotai/Kimi-K3))

The official vLLM recipe recommends at least eight GB300 GPUs (or eight MI355X/MI350X GPUs) and says multi-node is needed for real production traffic. It includes tuned TP/EP, FP8 KV-cache, prefix caching, and an optional DSpark draft model. ([vLLM K3 recipe](https://recipes.vllm.ai/moonshotai/Kimi-K3)) Baseten likewise reports eight GB300 GPUs and >1.4 TB of MXFP4 weights for K3. ([Baseten launch report](https://www.baseten.co/blog/how-to-build-a-day-zero-api-for-kimi-k3/)) Nebius reports 120 tok/s single-stream on eight B300 GPUs after substantial serving optimization. ([Nebius webinar](https://nebius.com/events/webinar-kimi-k3))

Kimi's K3.1 Pro guide says the full model weights will be released by **November 4, 2026**. On October 27, 2026, no K3.1 Pro weight repository or self-hostable K3.1 deployment recipe was available in the official documentation checked here. The OpenRouter description calling K3.1 Pro “open-weight” is therefore a forward-looking release description on this date, not an immediately usable self-hosting option. ([K3.1 Pro guide](https://platform.kimi.ai/docs/guide/kimi-k3-1-pro-quickstart), [OpenRouter model page](https://openrouter.ai/moonshotai/kimi-k3.1-pro))

## Bottom line

For the current 3D-builder workload, first try OpenRouter's `moonshotai/highspeed` route: it is the only materially faster K3.1 Pro route reachable with the existing key and was 2.7× faster in the controlled 5,000-token stream. Expect roughly double output cost, and benchmark quality/verbosity because the two runs produced different reasoning-token counts. A direct Moonshot Highspeed key or Kimi Code Pro subscription is the same basic speed tier. K3 has faster independent provider benchmarks and promising dedicated deployments, but switching from K3.1 Pro changes the model and requires another provider/key. Self-hosting is not a near-term escape hatch: K3 requires an eight-GPU-class installation, and K3.1 Pro weights were not yet released on this date.
