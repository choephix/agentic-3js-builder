## Goal (Stefan, 2026-10-24)

- A single-run build an app can show in about **one minute**, and **something on screen as early as possible** even if the full model arrives later. Cut anything that doesn't change what ends up on screen.
- **Quality is Stefan's call**, from the verdict pages (`bakeoff/gap*_page.py`). Model judges, LLM critics and an agent's own impressions of a render are not evidence; the judge-based conclusions in `STATUS.md` are unconfirmed for that reason. Facts that don't need taste (wall time, tokens, module size, crash and typecheck counts, overlap with examples) are what these experiments measure. Quality rows are left for Stefan.

## Where the time goes

Sonnet 5.5 streams at ~132 output tokens/s (Opus 5.5 ~102, Fable 5.1 ~74, Haiku 5.5 ~210). Wall time is billed output tokens ÷ that rate; the 84k-token prompt is cached and prefills in seconds. One craft3 build at high effort (r24, 124 builds):

| Share of billed output | Tokens (median) |   Time | What it is                                     |
| ---------------------: | --------------: | -----: | ---------------------------------------------- |
|                    86% |            ~55k | ~7 min | thinking (returned only as a 36k-char summary) |
|                    14% |             ~9k |  ~68 s | the module (24.5 KB)                           |

Estimate: billed completion tokens minus code chars ÷ 2.8 minus prose chars ÷ 4.2. So **the code alone is already about a minute; thinking is the other seven.** Textures and paint are 14–25% of module chars, so deferring them saves at most ~15 s of the code minute.

Readings:

- **Thinking buys correctness, not size.** r22nothink wrote modules as big as r24's in a fifth of the time; half of them crashed. Its crashes are API-shape guesses, not design failures: `hit.point` / `hit.p` for a Spot's position, `{x, y}` on a SweepPoint, a paint where a colour string goes, `{x, y, z}` objects for `[x, y, z]`, a `[x, y, "sharp"]` outline. 12 of the 14 have TypeScript errors; `npm run typecheck -- <file>` finds them in under a second. The check pipeline skipped typecheck (`typecheckSkipped: true`) and the repairs were whole-module rewrites (`r22nothinkfix`: 13k tokens, 1.1 min).
- **Max effort is unusable single-run:** 10/10 spent the whole 128k cap thinking.
- **Ambition is the other axis.** The early prompt (r2) got 6.6 KB modules in 56 s; the lean brief (r22lean) 11.5 KB in 2.4 min at low. Whether the smaller modules are acceptable is a verdict-page question nobody has answered: `bakeoff/judging/` holds Stefan's phase-2 verdicts only, none for the r20–r22 speed arms (`gap3/`).
- **The gateway can't switch thinking off for Sonnet 5.5.** `--no-thinking` omits the parameter and pins effort low; 21/25 r22nothink replies still carried a thinking block. `budget_tokens` is dropped for adaptive models. A "no thinking" arm run through it measures the gateway, not the model.
- Opus 5.5 at high was slower and dearer. Stefan's only verdict so far: one Opus part (a snowflake) is wildly goofier than anything he has seen; the rest is unjudged.
- **Fable 5.1 at low (r25fable)** on 5 briefs Sonnet and Opus built at high in r24 (ramen stall, mimic chest, alebrije, zeppelin, tin robot), run one at a time: medians 6.9 min, 28.9k output tokens (~24k of it thinking), 22.8 KB, $1.47 once the prompt is cached (the first run paid the $1 cache write: $2.75). The same 5 on Sonnet high: 7.4 min, 56.9k, 21.3 KB, $0.74. Fable thinks about half as many tokens at low as Sonnet does at high, but streams at ~74 tokens/s against ~130, so wall time comes out the same and each build costs about 2×. Its code alone (~6k tokens) takes ~85 s, so Fable can't reach the one-minute goal even with no thinking. All 5 render; the tin robot has one type error (`.bone` on `PartOptions | undefined`). $8.06 moved stefan@revoltage.io's 7-day Fable meter 28 → 30 (whole-point readings; the catalog session measured ~$7.4 a point). ## Stefan's hypotheses, answered

- **"Is it 90% thinking?"** Yes: ~86% of billed output at high effort, ~7 of 8 minutes. The module itself is already about one minute.
- **"Yield a partial result without textures first."** Measured at medium (`r32flat`): a prompt without texture asks cut thinking 39% and time from 141 s to 89 s, far more than the ≤15 s of writing estimated here before; the saving is thinking, not code. Textures can come back in a second pass: the model writes no UVs, since every SDK helper gives its surface paint coordinates (`docs/conventions.md`, "Paint surface coordinates") and a texture is an option on the part call. See "Two-stage build with requests" below.
- **"Put the plan in the output."** The thinking summaries show what the 55k tokens do: the build sheet (skeleton plan, limb placement, numbers). A bounded visible build sheet (≤40 lines) is the standard substitute for thinking when thinking is off, and it survives any reordering we impose on the code. Tested as E4 in r32 at medium: no effect. The model thinks as long, then writes out the plan it already made.
- **"Maybe I'm overthinking it."** My read: the hidden thinking and a visible plan don't stack well while adaptive thinking is on (the model thinks and then writes the plan it already made). Low effort stays the floor because quality is the bar (Stefan, 2026-10-25), so the remaining cut has to come from the model needing less deliberation: examples and templates, measured as billed thinking at low. Plan-vs-no-plan is a smaller question after that.
- **"Build more machinery beforehand; examples and templates."** The no-thinking crashes are exactly the class that in-context code fixes (the model copies field names and argument shapes it has seen) and that machinery fixes (fewer shapes to guess). Stefan's refinement, parts catalogs and then whole-subject samplers, ran in r26–r31 and is dropped (see "Catalog pilot (E2)" below); the API-shape side is P6 and the `--types` repair of P1.

## Routes to explore (Stefan, 2026-10-25)

First runs: r33 (readings above). For the next runs Stefan wants low effort before high, and builds no slower than medium's ~2.5 min. Every idea in this file, with its status, numbers and lineage, is drawn on one page: `map/index.html` under the public output folder (built by hand on 2026-10-27; update it when an idea changes status).

**Two-stage build with requests.** Stage 1 builds the model in flat colours and ends with a list of requests for stage 2: details to add and textures to paint, each tied to a part and a place. Asking for the list tells stage 1 that a second stage is coming, so it leaves room for what it requested instead of building emblems and stripes as geometry (the `r32flat` prompt asked for exactly that). Stage 2 works through the list, plus a share of its own ideas, instead of inventing at random. The list also makes stage 2 parallel: each request is one call, all run at once, assembled like parallel parts (`scripts/bakeoff.ts`, `assemble`).

- Requests that add parts are append-only and parallelise cleanly: each carries its anchor (a mount or frame on a stage-1 part) and what to build there; its call returns one function; the assembler appends it.
- Requests that change an existing part (a texture on the cab door) need an edit to stage 1's code, which parallel calls can't make safely. They run as one sequential edit call, or the SDK gets a call that paints an already-built part by name (E6's missing piece), which makes them append-only too.
- Stefan, 2026-10-27, on delegating stage 2: stage 1 does its best within its output budget and leaves its to-dos explained in the code; stage-2 calls each take a group of them in parallel. Open: how to split the work programmatically. Tag each to-do with a kind (texture, add-part, …) and hand each kind to one call in bulk, or give every to-do its own call; worth testing both. Swapping models and effort per stage is part of the space.
- Measure: stage 1's time and thinking with the request list against `r32flat` (the list may bring some texture thinking back); stage 2's wall time; whether stage 2's additions land where stage 1 left room (loose parts, envelope). Variant: stage 1 as parallel parts.

**Base-first parts (Stefan, 2026-10-27).** A child of parflat and two-stage. One call builds a bare base (chassis, hull, body) and ends with the parts list: an anchor, a box and a brief for each; the part calls then run at once, each given the base's code, so they place against real geometry instead of the plan's numbers (parflat's parts stick out past their boxes in every build; the box check fixes the bounds but not how a part sits on the body). Dropping the separate plan call keeps the critical path at base + slowest part: estimated first look ~20 s and final ~45 s at low, not run. Test it against parflat + the box check alone, in one batch at low.

**Haiku render loop.** Neither agentic nor a single run. Haiku 5.5 at low effort writes a module; it is rendered to one contact sheet with every view; the next single call gets the sheet (from the second turn on, the before and after sheets) and is told to fix what is wrong and add detail; repeat a fixed number of turns (20), since nothing decides when it is done. Variant: a fix call and an add call per turn, in parallel. The output is a page with a slider over the 20 frames, to see how the model evolved or got worse. In an app each frame replaces the model on screen, so the user watches it build itself. Best case: Sonnet-high quality at the same or lower time and price.

- Mostly existing machinery: `refine` with `--views` sends the renders and takes SEARCH/REPLACE edits (`prompts/refine-critique.md`), so 20 chained `refine` rounds with `--model` Haiku are the driver. New: the before/after pair in the prompt, the slider page, and the fix/add pair (two edits from one base can collide; alternating fix and add turns avoids that).
- Starting facts: Haiku streams ~210 tok/s. Haiku-100 (agentic, high effort) made complete but simpler builds, about half Sonnet's parts and triangles. Sonnet critique turns improved their input in phase 1, but by model judges, so that is unconfirmed.
- **Verdict (Stefan, 2026-10-27): parked; not worth it as run in r33.** The final frames do look better than frame 0, but not enough to justify the ~200 s of turns, and frame 0 itself took ~100 s, so the first look was no faster. The result stays far from Sonnet's builds: the turns mostly move small pieces around. The progression itself could be good to watch in an app as the model morphs into a more detailed version of itself, so the idea stays on the list.
- If it is picked up again:
  - Start from Sonnet low in flat colour (the current favourite) or a two-stage first look (~21–24 s), so Haiku only runs the turns.
  - A turn prompt that asks for bold improvement, structural changes included, while watching for parts that look wrong, instead of nudging small pieces.
  - Run Haiku on the flat-colour, geometry-only variant too: flat colour improved Sonnet's geometry, and may do the same for Haiku.
  - Give the views as separate images instead of one collage. r33 sent one 3×3 contact sheet per frame (`scripts/render-loop.ts`), so each view reached the model at roughly a third of the sheet's width.

**A model-native SDK (Stefan, 2026-10-27; an open musing, nothing planned).** OpenAI models (Sol, Astra, Terra) may do worse with the SDK partly because Claude models wrote almost all of it: the API, `docs/api.md`, `docs/conventions.md` and the arm prompts. Would a GPT model do much better with a version of the SDK it wrote itself?

- Sharper form of the idea: an API carries its author's guesses (names, argument shapes, what may be null). A model that guesses the same way needs less from the docs; one that guesses differently writes type errors. "Generic and self-explanatory" doesn't remove this: `chain.tip` vs a last-joint getter, `[x, y, z]` vs `{x, y, z}`, a colour string vs a paint are arbitrary choices.
- What r35 shows (reading of the `r35*/checks` records, 2026-10-27): 131 of 200 Terra builds have type errors, against 28 of 120 Sonnet builds. Terra's errors are concentrated: `Joint | null` passed where a joint is required (`parent: chain.tip`) accounts for ~230 of its errors, then `[x, y]` outline points where `[x, y, "sharp"]` was expected (48), and a paint or an `Rgb` where a colour string goes (~80). Sonnet's few errors are mostly the colour-vs-paint kind. The type declarations in the prompt cut Terra's `chain.tip` crash from 11/20 to 2/20, so reading more fixes much of it.
- Confounders: Terra thinks little at every effort and streams ~55 tokens/s, so even a perfect fit can't make it fast enough for the one-minute goal; some of its errors are its own code (undefined constants), not the SDK.
- Tests, cheapest first: (1) zero tokens: an error-shape census per model family across all rounds, which doubles as the candidate list for the forgiving API (P6); (2) a dialect layer: accept the top GPT guesses (a non-null `chain.tip` falling back to the last joint, two-number outline points, colour-or-paint) and rerun Terra on the 20 r35 briefs; if its crash and type-error rates fall to Sonnet's, the gap was guessability; (3) a GPT model rewrites `docs/api.md` and the arm prompt in its own words over the same SDK, to separate the docs' voice from the API; (4) only if a gap remains after 2 and 3: a GPT model designs its own SDK, compared on the same briefs. Step 4 changes the SDK's quality along with its author, so it can't isolate the effect alone.
- r37 (2026-10-27, page `r37/` from `scratch/r37/page.py`): Sol and Astra fail as often as Terra on the current SDK, and 61 of the 106 GPT first-render crashes are one error, a `null` joint passed as `parent` or `bone` (the `chain.tip` guess).

## Catalog pilot (E2), design

**Dropped for good (Stefan, 2026-10-25).** No speed gain at low, medium or high effort, no visible gain, and a risk of samey builds. `catalogs/` stays in the repo as a record only.

Stefan's idea (2026-10-25), replacing whole-module examples: a **sampler** is one whole subject with everything for that subject on it: a complete base (a pickup) with several constructions of each of its parts attached and named by slot and variant (`wheelOffroad`, `wheelSpoked`, `headlightSlit`, `cabBoxy`). A cheap router (or a tag match) picks a few samplers whose subjects the prompt should borrow from, and the builder blends them into the requested subject: it picks the parts it likes and makes them its own, with an instruction to exaggerate and blend, not take as is. The test hand-picks the samplers.

**Samplers are whole subjects, not part families (Stefan, 2026-10-25).** For "futuristic militarized truck from 2077" the story is that the router picked four samplers for inspiration: one everything-truck, one everything-tank, one everything-mounted-weapons platform (lasers and the like), and one spaceship for the futurism. Each is a complete subject of its own that the builder blends from. The first set in `catalogs/` got this wrong: apart from the truck it splits parts by family across subjects (loose track units and armour plates, a weapons shelf with rifles in racks, a hull-greeble shelf, a materials sheet), so no tank or spaceship exists in it to borrow from. It stays as a comparison arm (C2 below).

Why it should beat whole-module examples: eight wheel constructions cost the tokens of one module; the names give the model, the router and the app one vocabulary; and the base with named attachment points is the template of the old E3, so this merges E2 and E3. Caching: the docs stay a fixed cached prefix; the picked samplers follow in a stable order (alphabetical), so a repeated combination reuses the cache and a new one pays one cache write. Four samplers at 30–40 KB each add ~35–45k input tokens to the 84k prompt; whether that much context changes thinking time is one of the facts the pilot records.

What it can't give, and the fixes:

- **Composition** (proportions pushed per style, paint by place, a setting fitted to the subject) comes from whole models. The base is a finished, complete model, not a bare frame.
- **Style.** Open question for Stefan: samplers painted in their own style (a whole model carries its paint, as it carries its composition), or painted plainly with style kept apart. The first set kept it apart in `materials2077.ts`; under the whole-subject framing the spaceship sampler is where the futurism comes from.
- **Breadth dilutes.** ≤8 variants per slot, each a different construction (not a colour variant) with a one-line comment saying what is different. Past that the model skims and leans on the first few. Variety comes from adaptation and exaggeration, not from 67 headlights.
- **Overlap is for the reader, not the model.** The model reads code; the render is Stefan's cull sheet. The sampler lays its variants out around the base on a board, labelled, so one render shows every recipe.
- **"Make it your own" at low effort** usually means changed numbers and colours plus one added element; a true blend of two recipes is rare. The instruction asks for exaggeration and at least one construction change per pick; the copy detector (8-gram overlap of each part function with the catalog) reports what happened; the verdict is Stefan's.

**Pick-first, the first-pixel path.** The reply opens with the pick list: slot → variant → stated deviation (`wheelOffroad → double-wide, 8 lugs, mud flaps`), ≤200 tokens, about 2 s. The app runs the primary sampler's assembly function (here the truck's) with those picks and shows a generic version at once, then swaps in the model's module when its fence closes. Picks from the other samplers join the placeholder only where they share the primary's mount convention, so all samplers use one `Mount` shape. No second call; the placeholder is sampler code, so it runs; and the stated deviation commits the model to adapting before it writes (the plan-first idea with a vocabulary, so it is cheap).

## Metrics every arm records

Per build: `wallMs`, `firstCodeMs`, `codeCloseMs` (after P3), billed output tokens, estimated code tokens, thinking block present, module KB, parts and textures (from the check), typecheck error count, first-render crash, repair calls and their time, cost.
