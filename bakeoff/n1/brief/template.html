What the SDK is

The model writes one TypeScript module against a set of modelling helpers instead of raw three.js. It lays out joints, sweeps tubes along them, extrudes plates, turns domes on a lathe and sticks parts onto the surfaces it has already built. The SDK returns a three.js object, which an app packs into a single mesh with one texture atlas, rigged when the model has joints. The library is about 9k lines, plus optional style kits for pixel, toon and clockwork looks.

The model gets the API reference and a page of conventions in its prompt, about 84k tokens that stay cached between calls. A typecheck runs on every module; if it fails, or the first render crashes, one cheap repair call sends back targeted edits.

How it would plug into Nilo

generate_low_poly_model keeps its schema. The client picks the engine by flag, and the stored model records engine: "sdk" so edits know which path to take. The World Agent's routing and tool docs stay as they are, and the flag gives an A/B on real prompts. The server adds a build role and a repair role to the existing code-generation callable; the client sandbox gets an SDK branch and reuses upload, spawn, draft display and task recording.

The engine in pseudocode 
// server: code-generation callable, new role "sdk-build"
system = [SDK_API, SDK_CONVENTIONS, SDK_DECLARATIONS, FLAT_PROMPT]   // cached prefix
src = fence(await sonnet({ effort: "medium", system, user: brief }))
errors = tsc(src, SDK_DECLARATIONS)                                 // ~1 s
if (errors.length) src = applySearchReplace(src, await sonnet({ effort: "low", repair: errors }))
return { js: stripTypes(src), source: src }

// client: sandbox harness, engine "sdk"
const root = (await import(blobUrl(js))).default()
const mesh = await createStaticMesh(root, name)   // createSkinnedMesh once a rig is used
mesh.userData = { lowPoly: { engine: "sdk", source }, entities: [name] }
glb = await exportGlb(mesh)                       // then the existing upload, spawn and record

What we learned

From about 30 rounds of controlled runs, each comparing setups in the same batch with 10 or more builds per setup.

  1. Reasoning effort is the quality dial, and time follows it. On these 20 briefs, one Sonnet call took {{low.final}} at low effort, {{medium.final}} at medium and {{high.final}} at high. Output speed barely moves; the extra time is thinking, about 1.8k, 17k and 55k thinking tokens. High effort gives visibly more detailed models: compare the last column of the gallery.
  2. Telling the model to think less does nothing. We tried a library of reference code in the prompt, an instruction to settle decisions first and write the code once, and a written build plan at the top of the module. None of them changed thinking time.
  3. Giving it less to do works. Dropping textures, so every surface is one flat colour, cut thinking by 39% and build time from 141 s to 89 s at medium. The model spent part of the saving on more geometry. Nilo's low-poly already works in flat colour.
  4. Splitting the work across calls that run at once works. A planning call followed by five part calls in parallel halved build time at medium, from 146 s to 71 s, and was faster on all 10 pairs, with about 2.7 times the triangles. Parts built by separate calls don't always fit together; checking each part against its planned box removed the overhang in a follow-up test. Two-stage reuses this machinery.
  5. Crashes are cheap to fix. A typecheck plus one repair call fixes nearly every crashed build in 3–6 s. Putting the SDK's type declarations in the prompt cut builds with type errors from 8 in 40 to 1 in 40, at no extra build time.
  6. Nilo's critic never approved a build. In 17 critiques it answered "revise" 17 times; the other 3 briefs crashed in their first round, leaving nothing to critique. So every brief paid for both rounds, and the final build is never reviewed.

Integration work, in order
  • SDK side. A browser bundle built against Nilo's three.js (0.186; the SDK is on 0.185). SVG textures need the DOM, so either the one-call prompt avoids them, or the sandbox draws them on the main thread (two-stage needs this). A Nilo variant of the prompt with Nilo's floor and scale.
  • Server. Build and repair roles in the code-generation callable, a typecheck against the SDK declarations, and prompt caching on the 84k-token prefix.
  • Client. The engine switch in the generator, an SDK branch in the sandbox harness that skips the per-mesh material checks (the atlas is one texture), and the engine stamp on the stored model.
  • Edits. Free-form and part edits as search-and-replace calls on the stored source. Palette and parameter edits stay deterministic only if the prompt asks the module to export them.

Decisions we need

  1. One tool with an engine flag, or a separate tool from the start? We lean toward one tool: the agent's routing stays as it is, and the flag gives an A/B. A separate tool makes sense once the SDK does something low-poly can't, such as rigged creatures.
  2. Sonnet 5.5 or Gemini 3.8 Flash? Sonnet is tested at {{flat.cost}} per model for one call. Gemini is Nilo's default and likely several times cheaper, but has never run on the SDK (next step 2).
  3. Static meshes first, or skinned meshes from day one? Skinned meshes would expose named joints to animation generation.
  4. Where should the SDK live? A package in the Nilo monorepo means about 9k lines in the first pull request. The alternative is a separate repo that Nilo consumes.
  5. One call only, or two-stage as well? Two-stage maps onto Nilo's draft entities and gives the more detailed model, but costs 7 more calls per model and needs SVG drawing outside the worker.

How we measured

Setup, caveats and the full numbers
  • Briefs and batch. All four new arms used the same 20 r24 rich briefs and ran together from 15:18:55 to 15:32:06 +02. Compare within this batch: another batch can be up to twice as slow.
  • More visual iteration favours today's loop. Low-poly gets a design call, up to two build rounds and a critique between rounds; the critic and next builder see four high-detail renders. The SDK gets one generation call and at most one repair, with no visual feedback.
  • Different correctness gates. Low-poly uses Nilo's runtime and scene validation; its failed sandbox result becomes feedback for the next round. SDK builds use an explicit TypeScript check and typecheck-gated repair, plus the SDK packing harness.
  • Prompt context differs. The SDK prompt includes about 74k tokens of library/API/style reference, mostly cached. Low-poly gets Nilo's smaller instruction pack, but its separate design answer supplies extra planning context.
  • Output headroom differs. These SDK runs allowed a 120k output cap; Nilo's shipped low-poly build turns use a 64k cap (with design and critique caps below that). Actual outputs were far below either cap. PR #13860 repairs after a failed sandbox run and has no typecheck; these bakeoff SDK arms used typecheck-gated repair.
  • Geometry budgets differ. Nilo guides props toward about 10k triangles and warns above 24 directly articulated entities (hard fail at 100k triangles). SDK docs target 180–340 parts, allow 1,000 parts and a 60k soft triangle budget (120k lab ceiling). That gives the SDK more geometry/detail headroom.
  • Rigging differs. The SDK prompt supports joints and skinned creature parts; Nilo's low-poly contract forbids SkinnedMesh and animation. The page shows static renders either way, and makes no visual verdict.
  • Textures are not the matched comparison. The fair pairs are SDK flat low/medium against Nilo Sonnet low/medium. The existing SDK Sonnet-low textured column is gallery context only. Low-poly forbids texture code; the table and tile markers count SDK svg() calls and texture: options, including leaks in flat prompts.
  • Caching and call count differ. Both use the local auth gateway and prefix caching. The SDK has a large static cached prefix; low-poly repeats role prompts and transcripts. Low-poly normally spends 3–4 or more turns per prop; SDK spends one plus a rare repair.
  • Runtime contracts differ. SDK modules are TypeScript imported and packed by the SDK harness; low-poly is import-free JavaScript run by Nilo's three.js sandbox. Neither is a neutral shared checker, so failures are not directly equivalent.
  • Rendering environment. Chromium renders used the NVIDIA RTX 3060. Model calls went through omp auth-gateway stdio rather than the Firebase callable, so production queueing and network latency are not measured.
  • Cost. Costs are list-price equivalents recorded by the gateway, with Sonnet's prompt prefix cache reads. The new batch totals about $16.72 across four arms; looks remain Stefan's call.
