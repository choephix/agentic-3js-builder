# Prompt bake-off

How well does a model build from one system prompt and one pitch, with no tools and no second turn, the way an app would run it? A bake-off sends the same pitches through several system prompts (arms) and shows the results side by side on the showcase's `/bakeoff` page.

A **single-run** build is one API request and one reply, with no tool calls. A later crash-repair call is a separate call and does not change that label; pipeline costs and call counts include repairs separately from the initial run.

The showcase's `/lab` page tells the whole story of every round so far: what was tried in which order and why, with a scoreboard, a filterable gallery, a compare grid with presets, charts of time, tokens and cost, failures by message, the pitches and the method. It reads every round from `lab.json` (`showcase/lab-data.mjs`); its thumbnails come from `npm run lab-thumbs`, a cache outside git that `showcase:build` fills. `npm run lab-export` writes a static copy to webshare, http://axalon:8080/nilo/agentic-3js-builder/lab/, that needs no dev server and links nowhere outside itself. Its viewer shows each build's render sheet and its exported GLB in 3D, with turntable, wiggle, skeleton and wireframe.

The last story chapter covers the single-run vs agentic gap study (rounds 5–9): stronger style briefs, kits and craft prompts, repair/critique chains, and the fixed two-turn held-out results from `docs/STATUS.md`. Compare presets open the 12 held-out briefs and the Sonnet/Sol development critique chains. The held-out contact sheet is a bundled asset (`showcase/lab-heldout-grid.jpg`), so the exported chapter keeps its agent-final comparison; later rounds may appear in the data without changing that recorded table.

The live, unjudged extension is generated by `python3 bakeoff/gap_page.py` at http://axalon:8080/nilo/agentic-3js-builder/gap/. Run it after each completed run/check/refine round. It reads results, checks and archived snaps; retains the original per-subject Sonnet/Sol comparisons and historical judge captions (hidden by default); and adds GPT-6 Astra (`r10astra*` held-out, `r11astra*` dev) and Gemini 3.8 Flash (`r10gem*`, `r11gem*`). Both use high effort, `craft2` from `arms-r8.json`, concurrency 8, up to two repair turns and two feedback turns with `refine-critique.md` and three-quarter/front/side/low views. Single-run limits are 120000 tokens for Astra and 65536 for Gemini; feedback turns use the Sol chain's 64000-token limit. Gemini uses only `google-antigravity/gemini-3.8-flash`, never a Cursor provider.

Phase 2: `python3 bakeoff/gap2_page.py` publishes http://axalon:8080/nilo/agentic-3js-builder/gap2/index.html with agent final/first draft, Sonnet/Astra/Haiku subject-only single-run builds, and **Sonnet · agent framing (app, multi-call · ~17 calls)** from `r18app`/`r18appb` and their crash repairs. The app draws each used 17 model calls before repairs; they are not single-run builds. Each API column has saved local verdicts and JSON export; adding a model preserves existing choices. There are no judge scores or visual-feedback turns.

The gap page has per-builder and stage filters, archived Astra and Haiku agentic finals (model IDs verified from each sample's build record), and the old lab prompt column. Haiku and the old lab prompt start hidden. The original Sonnet agentic final stays first, outlined in green. Missing/unchecked builds and crashes remain visible as labelled tiles. Regeneration makes no API calls and performs no judging.

`python3 bakeoff/replay_page.py` and `python3 bakeoff/replay_page.py --experiment replay2` regenerate the replay pages. C is the single-run craft3 control. The other variants use tool conversations: R took 1–4 model calls per draw, S 2–9, V1 1–3, V2 4–9 and V3 2–9, before separate crash repairs. Even a tool conversation that returns its sample write in the first reply is not a single-run build.

Round 10/11 outcomes: Astra's final feedback rounds render 12/12 held-out and 16/16 dev builds. Gemini's held-out final round renders 10/12; soulScythe and treasureHoard crash. Its dev gnomeTinkerer was still broken after the two-repair limit: the runner automatically repaired it again in `r11gemc1`, then critiqued it in `r11gemc2`. Those over-limit records and their spend remain archived, but the comparison keeps gnomeTinkerer at its capped, crashed `r11gemfix2` result in both stages. Other feedback rounds may repair regressions instead of critiquing them (the runner's existing behaviour); tile captions state actual critique/repair counts rather than claiming two critiques for those cases. No gateway errors occurred. Total estimated API spend, including over-limit calls, was $85.8271.

## Agent framing an app can run

`bun bakeoff/replay.ts --app` runs all 28 phase-2 briefs with Sonnet 5.5, high effort and 120000 max tokens. A single fixed wizardBookshelf system and campaign-brief template are filled with the slug, sandbox, Category, Subject and Style; no subject-specific archived conversation is used. Synthetic reads supply the current GUIDE, API/conventions, `src/paint.ts`, `src/math.ts`, and selected kit docs/sources. The fixed style mapping and feature-based clockwork/glow additions are saved in `round.json`.

The model can write and hashline-edit its virtual `samples/<slug>.ts` until it ends naturally or yields, with at most 16 calls after the initial request. Its visible filesystem contains only `src/`, `kits/`, `docs/`, `scripts/`, GUIDE, package/TypeScript config files and its own virtual sample. Other samples, archived rounds, showcase and host paths return "No such file or directory", through relative and absolute aliases alike. Safe inspection bash is tokenized, path-mapped and quoted before execution. Scratch mkdir/touch/cd/rm/rmdir operations are acknowledged without mutating the project; requested typechecks run the real targeted project compiler on a temporary import-wired copy. The native OMP read/edit implementation supplies snapshot tags and edit semantics, with formatting, LSP diagnostics and automatic model-based edit repair disabled. After the third refused render/preview/probe request, the tool result explicitly asks the model to end its turn if the file is complete. The last stored module, not its first write, is the deliverable.

Requests, replies, tool results, writes/edits/typecheck/refusal counts, stop reason, usage, spend and wall time are recorded in `r18app`. An Anthropic 5-hour usage reading above 50% pauses new calls; the current campaign spend guard reserves headroom below the approved $90 total, including the original draws. After generation, `check --skip-typecheck` renders final modules, then at most two craft3-system `--repair-only` rounds fix crashes. `--app --app-round r18appb --subjects kraken` makes a targeted replacement draw with the sealed harness; the gap2 app column prefers that round and its repairs where present and labels every selected round. Captions include the whole app loop and repairs. `--prepare-only --app` writes fixed inputs without calling a model. `bakeoff/app-inputs/audit.json` retains the original campaign's full restricted-scope tool-call audit.

## Pieces

- `arms.json`: each arm is a contract, an optional taste paragraph and a reference.
  - **Contracts:** `prompts/contract.md` for SDK arms, `prompts/contract-plain.md` for three.js only.
  - **Taste:** `prompts/taste-sdk.md` builds with the SDK throughout; `prompts/taste-primitives.md` puts simple primitives first and uses the SDK only where primitives fall short.
  - **Reference:**
    - `source`: every `src/*.ts` file, about 69k tokens.
    - `docs`: `docs/api.md` and `docs/conventions.md`, about 23k tokens.
    - `brief`: the top of `docs/api.md` up to "Frames" (helper map, cheat sheet, target, module), about 4k tokens.
    - `none`.
  - **Optional fields:** `kits: true` adds every style kit's doc and source (importable as `agentic-3js-builder/kits/<name>`); `sources` adds named `src/` files verbatim; `extra` adds prompt files after the taste (`ambition.md`, `craft.md`, `craft2.md`); `plan` makes the model write a build sheet from that prompt file (medium effort) before the module, in the same conversation.
- `pitches.json` (round 1), `pitches-r2.json` … `pitches-r4.json`: subjects (creatures, a humanoid, a prop, a diorama), each with a `terse` and a `rich` pitch of the same subject. `pitches-r5.json` (16 dev subjects) and `pitches-r7.json` (12 held-out subjects) carry the exact Category/Subject/Style briefs the agentic Sonnet builders got, so a single-run build can be compared with that sample.
- Other arm sets: `arms-r5.json` (docs, kits, kitsamb), `arms-r6.json` (craft), `arms-r8.json` (craft2, craft2plan).
- `rounds/<round>/`: one run of arms × subjects × levels:
  - `round.json`: model, effort, arms and pitches as run.
  - `prompts/`: the exact system prompts.
  - `runs/`: request record and reply per build.
  - `builds/`: the modules.
  - `checks/`: type errors and the render report.
  - `results.json`: all of the above in one file.

The model's reply is one fenced TypeScript block. Its module imports `three` and `"agentic-3js-builder"`, which the runner points at `src/index.ts`. The module default-exports a no-argument function that returns the model.

`bun bakeoff/replay.ts --single` runs `r19single`; add `--craft` for `r19craft` with `prompts/craft3.md` as another pre-read file. Both reuse the frozen app framing, prefill orientation and SDK/glow lookups, and extract the complete `write` from one high-effort Sonnet 5.5 reply (120k cap, automatic tool choice, no tool results returned). The recorded r19 arms used eight workers; `--workers N` now defaults to 16 and resumes existing runs. `--subjects koala,treasureHoard --generation-only` selects a pilot. A missing write permits one fresh redraw; render crashes permit two separate repair calls (`fix`, `fix2`). `gap2/` captions separate generation, redraw and repair counts. Requests, replies and accounting are retained. The r19 arms share a $60 cap including repairs and pause above 50% Anthropic 5 Hour usage.

`--single --effort low|medium|high` changes only `output_config.effort` (default `high` preserves r19 requests). The r20 sweep runs `r20medsingle`, `r20medcraft`, `r20lowsingle` and `r20lowcraft` with the exact corresponding frozen r19 inputs, adaptive thinking, unchanged 120k cap, redraw and two-crash-repair policy; repairs use the same effort. Low-effort koala/treasureHoard pilots precede the full 28-subject arms. The sweep began with eight workers and a shared $70 cap; the orchestrator later raised the cap to $90 and resumed the remaining three arms concurrently with `--workers 16`. The same above-50% Anthropic 5 Hour pause applies; per-arm `*-inputs/report.json` retains accounting and notes the restart. Regenerating `gap2_page.py` adds medium/low single/craft columns after the original high-effort pair without replacing saved verdicts.

`--single --ref --effort low` runs `r21reflow`: the frozen `r19single` framing and unchanged brief, with one extra prefilled `read` of `<sandbox>/refs/<slug>.png` returning a base64 PNG image block before the final complete-write instruction. The selected neutral/styled sheet is recorded per subject in `round.json` and `r21reflow-inputs/report.json`; the model is asked to match its silhouette, proportions, palette and signature features while retaining the brief's staging. There is no craft read; adaptive thinking, the 120k cap, one no-write redraw and up to two crash repairs are unchanged. The full run uses `--workers 16` (increased from the original eight at the orchestrator's request). The arm has a separate $40 recorded-spend cap including repairs and pauses above 50% Anthropic 5 Hour usage; requests interrupted before returning usage are listed separately in the report. Pilot with `--subjects koala,treasureHoard --generation-only` before the full 28 subjects; the `gap2/` reference-low column links a thumbnail of each sheet alongside its build caption and preserves existing verdicts.

### Gap3: asset framing and static models

`replay.ts --single --craft --effort low --round <round> --workers 12` supports these request ablations while leaving the existing r19/r20 flags unchanged:

| Round        | Extra flags                                                               |
| ------------ | ------------------------------------------------------------------------- |
| `r22asset`   | `--prompt-file bakeoff/prompts/asset.md`                                  |
| `r22norig`   | `--no-rig`                                                                |
| `r22lean`    | `--prompt-file bakeoff/prompts/asset.md --no-rig`                         |
| `r22cap`     | `--prompt-file bakeoff/prompts/asset.md --no-rig --thinking-budget 10000` |
| `r22nothink` | `--prompt-file bakeoff/prompts/asset.md --no-rig --no-thinking`           |

The prompt-file flag replaces only the craft pre-read slot, preserving the assistant-read/tool-result shape. `--no-rig` deterministically removes skeleton/answer-key/posing sections, rig options and guidance from every system, assignment and prefilled read; SDK implementation reads become compiler-emitted public declarations with rig members removed. The exact request-only views and removed-section ledger are in `norig-inputs/`; the SDK files are not stripped. A final positive instruction requests a static asset in model space with no joints. The SDK supports these models under an untagged root, exporting zero joints.

Gap3 uses the 25 app briefs other than elvenArcher, cyborgMedic and gnomeTinkerer. `--only koala,treasureHoard --generation-only` selects pilots; `--prepare-only` recreates inputs without model calls; `--check-only` runs render checks and up to two crash-repair rounds without generating new initial modules. Gap3 repairs reuse their arm's exact sanitized reads and thinking settings and request a complete corrected write, rather than the older generic refinement prompt. `--thinking-budget N` sends `thinking: {type: "enabled", budget_tokens: N}` with the chosen effort. The gateway accepts this but drops the budget for adaptive Sonnet 5.5: `r22cap` is honestly labelled a second draw of C (adaptive + low effort), not a hard-capped arm. `--no-thinking` requests disabled thinking; the gateway instead omits the thinking parameter and pins effort low, so the API default applies. `r22nothink` measures that behaviour without claiming zero reasoning. Both saved probes include source evidence; every build records thinking-block presence, billed output tokens and estimated code tokens.

All five Gap3 arms share a $70 spend guard, including repairs, probes and discarded pilot accounting, with cross-process in-flight reservations. Anthropic 5-hour usage above 50% stops new requests. Saved requests/replies and build records retain timing, output tokens, cost and module bytes. `uv run --with tiktoken==0.14.0 python bakeoff/gap3_report.py` writes each `r22*-inputs/report.json` and fills per-build code-token estimates using the same o200k estimator as earlier rounds; the non-code residual includes tokenizer mismatch and is not an exact reasoning-token count. `gap3-request-audit.json` records the 25-subject and no-rig/prompt-slot evidence.

## Feedback turns

`refine <round> --from <source>` gives every build of the source round one more turn, as an app would after running the module. The conversation is the arm's system prompt, the pitch, the current module as the model's own reply, and the feedback:

- **Repair**, when the module failed: the error (`prompts/refine-repair.md`).
- **Critique**, when it built: the snap's shots as images (`--views`) and its measurements (counts, size, issues, loose parts), with `prompts/refine-critique.md` or another `--critique` file. `--critic <model>` lets a second model write the change list from the renders and the code (`prompts/refine-critic.md`) and the builder makes it (`prompts/refine-apply.md`).

The reply is SEARCH/REPLACE edits (`prompts/refine-edits.md`) or a whole module. The new round's slugs swap the round prefix (`r6RedPandaRichCraft` → `r6c1RedPandaRichCraft`); `chainCostUsd` sums the chain. `--from a,b` takes each build from the first listed round that has it, so a repair round can lead the round it repaired. A check that can't reach the shared browser leaves the build unchecked rather than recording a failure.

## Judging

`judge.py` scores rendered builds blind with vision models through the same gateway (usage in its docstring). `judging/<panel>-spec.json` lists each subject's candidates by snap prefix; `judging/<panel>-judged.json` holds every judgment (scores per candidate, defects, ranking). The panels of the single-run vs agentic study (docs/STATUS.md, 2026-10-15) are there.

## Commands

```
npm run bakeoff -- prompt <arm>            # write an arm's system prompt to scratch/bakeoff/ and print its size
npm run bakeoff -- run <round> [--model anthropic/claude-sonnet-5-5] [--effort medium] [--arms a,b] [--subjects x,y] [--levels terse,rich] [--concurrency 8] [--arm-set arms.json] [--pitches pitches.json]
npm run bakeoff -- check <round>           # typecheck and render (snap tag v01) every build without a check yet
npm run bakeoff -- refine <round> --from <round>[,<round>] [--model …] [--views …] [--critique file.md] [--critic model] [--repair-only]
npm run bakeoff -- results <round>         # rebuild results.json
npm run lab-thumbs                         # thumbnails for the /lab page (missing or outdated ones only)
npm run lab-export                         # static /lab copy on webshare (rerun after new rounds)
```

- `run` only asks for builds that have no run record yet, so an interrupted round resumes where it stopped. To retry a build, delete its `runs/<slug>.json`.
- Round ids are letters and digits. Slugs are camel case, e.g. `r1FennecTerseDocsSdk`.
- Calls go through `omp auth-gateway stdio`, which uses the stored omp logins and adds about 50 tokens to the prompt. Any model `omp models` lists works.
- `costUsd` is estimated from `omp models --json` prices: uncached input, cached input and output. Cache writes aren't reported, so they're priced as plain input.
- `check` renders with `SNAP_RENDER_ON_ERROR=1`: a build the creature lab would reject (say, meshes on no bone) still renders, as a static mesh when its skeleton fails, the way an app would show it. Its report keeps the errors.
